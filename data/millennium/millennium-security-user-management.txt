# Cerner Millennium Security and User Management Guide

## Overview

Cerner Millennium uses a layered security model to control user access to patient data, clinical applications, and administrative functions. Security is managed through three interconnected concepts: Personnel (PRSNL) records, Positions, and Security Objects. This model ensures that each user has access only to the clinical data and application functions appropriate for their role and work location.

Millennium integrates with enterprise identity management systems (typically Microsoft Active Directory) for authentication and user provisioning.

## Authentication

### Active Directory Integration
Millennium uses Kerberos-based Active Directory (AD) integration for user authentication. Users log in once to the Windows workstation and are automatically authenticated to Millennium via SSO (Single Sign-On) — no separate Millennium password prompt appears.

Key configuration:
- Millennium must be registered as a Kerberos service principal in AD.
- Each user's PRSNL record must be linked to their AD username (User Principal Name).
- Group Policy enforces password complexity and expiration rules at the AD level.

### Multi-Factor Authentication (MFA)
Remote access to Millennium (via Citrix, VDI, or VPN) requires MFA. Oracle Health supports:
- Microsoft Authenticator (TOTP)
- RSA SecurID hardware tokens
- SMS-based one-time passwords (OTP)

MFA configuration is managed in the organization's identity provider (Azure AD, Okta, etc.) — not within Millennium itself.

### Break-Glass (Emergency Access)
Break-glass allows authorized users to access a patient record outside their normal security scope in emergencies. Every break-glass access is:
- Logged to the audit trail with reason code and approver
- Reviewed by the Privacy Officer on a scheduled basis
- Alerting Privacy/Security team via automatic notification

## Personnel (PRSNL) Records

Every Cerner Millennium user requires a PRSNL (Personnel) record. The PRSNL record stores:
- prsnl_id — unique numeric identifier (f8)
- name_full_formatted — display name
- username — linked AD account (User Principal Name)
- position — the user's clinical or administrative role
- home facility — primary work location
- Active/inactive status

### Creating a PRSNL Record

1. Open Personnel Manager from the Cerner administrative tools.
2. File > New Personnel Record.
3. Enter: Last Name, First Name, Middle Initial.
4. Enter the user's Active Directory username in the Domain Username field.
5. Set the user's Home Facility and Cost Center.
6. Assign a Position (see Positions section below).
7. Assign Locations (see Locations section below).
8. Set status to Active.
9. Save. The system generates a unique prsnl_id.

### Modifying a PRSNL Record
Changes to positions, locations, or status take effect immediately upon save and next login. No application restart is required.

### Deactivating a User
Never delete a PRSNL record — it is referenced throughout the clinical history. Instead:
1. Open the PRSNL record in Personnel Manager.
2. Set Status = Inactive.
3. Set an end date for all Position/Location assignments.
4. Save.
The user will be unable to log in but their historical data remains intact.

## Positions

A Position is a role template that groups together:
- Security Objects (application feature permissions)
- Default printer assignments
- Default view settings
- Time and attendance codes

Common positions include: RN-ICU, Pharmacist, Attending Physician, Admissions Clerk, Lab Technician, System Administrator.

### Assigning a Position to a User
1. Open the user's PRSNL record in Personnel Manager.
2. Go to the Positions tab.
3. Click Add and select the position from the list.
4. Set an effective date and optionally an end date.
5. Mark the position as Primary if it is the user's default context.

### Creating a New Position
1. Open Position Manager (requires Security Administrator access).
2. File > New Position.
3. Enter Position Name and Description.
4. Go to Security tab > Add Security Objects one by one (or by group).
5. Configure default printer, printer group, and workstation settings.
6. Save.

## Security Objects

Security Objects are the granular permissions that control what a user can see and do in Millennium. Hundreds of security objects exist covering every application, screen, button, and data element.

Examples:
- CPOE_ORDER_ENTRY — ability to enter orders in PowerChart
- CHART_REVIEW — ability to open and read patient charts
- DISCERN_ANALYTICS_DEV — ability to create CCL scripts in Discern Explorer
- ADMIN_POSITION_MGMT — ability to manage positions and security
- BREAK_GLASS_ACCESS — ability to invoke break-glass on out-of-scope patients
- PHI_ACCESS_AUDIT_VIEW — ability to view audit logs

### Adding Security Objects to a Position
1. Open Position Manager.
2. Find and open the position.
3. Go to the Security Objects tab.
4. Click Add and search for the security object by name or keyword.
5. Save. Users in this position receive the new access on their next login.

### Security Object Groups
Security objects are organized into groups for easier administration. Assigning a group applies all objects within it. Common groups:
- POWERCHART_RN — standard RN access package
- PHARMACY_STANDARD — standard pharmacist access
- ADMIN_CLINICAL — clinical administration access

## Locations

Locations control which facilities and units a user can access clinical data for. Without a Location assignment, a user cannot view patients in that area.

Location hierarchy:
- Organization (top level) → Facility → Building → Unit/Department → Bed

### Assigning Locations to a User
1. Open the user's PRSNL record.
2. Go to the Locations tab.
3. Click Add and navigate the location hierarchy to select the appropriate unit(s).
4. Set effective dates.
5. Mark one location as the Home Location.
6. Save.

### Float/Multi-Location Users
Staff who float between units need multiple location assignments. Add each unit they regularly work in. Use broad location assignments (e.g., the entire facility) sparingly — over-broad access increases HIPAA risk.

## Audit Logging

All Millennium user activity is captured in an audit log:
- Every patient chart opened (person_id, encntr_id, prsnl_id, timestamp)
- Every order placed, modified, or cancelled
- Every clinical document created or signed
- Every security administration action (position changes, user creation)
- Every break-glass access event

### Viewing Audit Logs
1. Requires the PHI_ACCESS_AUDIT_VIEW or equivalent security object.
2. Open the Audit Log Viewer from Security Administration.
3. Filter by user, patient, date range, or event type.
4. Export to CSV for external reporting.

### HIPAA Compliance
The audit log satisfies HIPAA Security Rule requirements for access monitoring. Organizations must:
- Review audit logs regularly (at minimum monthly) for suspicious access patterns.
- Investigate all break-glass accesses within 24 hours.
- Retain audit logs for at least 6 years per HIPAA requirements.

## Single Sign-On Configuration

### SAML 2.0 SSO (for Web-based Cerner Applications)
For web-based Oracle Health applications (PowerChart Touch, HealtheIntent, SMART on FHIR apps):
1. Configure your IdP (Azure AD, Okta, Ping) as a SAML 2.0 identity provider.
2. Register Oracle Health as a SAML service provider in your IdP.
3. Map IdP user attributes (UPN, groups) to Millennium PRSNL records.
4. Test with a pilot group before enabling broadly.

## Best Practices

1. Follow least-privilege — assign the minimum security objects needed for the user's role.
2. Never share credentials — each user must have their own unique PRSNL record and AD account.
3. Review access quarterly — run the Access Review report to identify users with excess permissions or stale access.
4. Deactivate, never delete — always deactivate PRSNL records when users leave; never delete them.
5. Test position changes in Training domain before applying to Production.
6. Document all break-glass events with a clinical justification.
7. Set position end-dates for temporary assignments (travelers, students, contractors).
